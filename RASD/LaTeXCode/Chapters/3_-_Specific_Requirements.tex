This section details the interfaces between the Best Bike Paths (BBP) system and external entities, including users, hardware components, other software systems, and communication networks. These interfaces define how BBP interacts with its operational environment.
\section{External interface requirements}
\label{sec:external_interface_requirements}%

\subsection{User interfaces}
\label{subsec:User_interfaces}%
The primary user interface for the BBP system will be a native mobile application designed for smartphones (IOS and Android platforms). The interface must prioritize clarity, usability, and robustness, particularly for outdoor use under varying light conditions. It will adopt a map-centric design, prominently displaying geographical data and path information. Key interaction elements will include a clear search bar for origin/destination input, interactive map elements for manual path creation and viewing details, easily accessible buttons for critical functions like starting/stopping automatic recording, and a dedicated Heads-Up Display (HUD) during active recording sessions showing real-time statistics (speed, distance, time) with high legibility. The interface will also incorporate clear feedback mechanisms and prompts for user input, such as review and confirmation of automatically detected sensor events presented at the conclusion of a trip . Navigation between different sections (e.g., Map, Search Results, My Trips, User Profile) must be intuitive and consistent throughout the application.

\subsection{Hardware interfaces}
\label{subsec:hardware_interfaces}%
The BBP system requires direct interaction with specific hardware components integral to the user's mobile device. Foremost is the Global Positioning System (GPS) receiver, from which the application must continuously acquire accurate location data (latitude, longitude, timestamp) to track the user's position during navigation and automatic trip recording. Secondly, BBP must interface with the device's inertial measurement unit (IMU) sensors, specifically the accelerometer and gyroscope. Access to the raw data streams from these sensors is mandatory for the implementation of the automatic obstacle detection feature, enabling BBP to identify significant motion events that may correspond to real-world path anomalies, such as potholes. Furthermore, the application relies on standard smartphone hardware, including the touchscreen display for all user input and output, and potentially the device's vibration motor for non-visual notifications (e.g., indicating a potential obstacle has been logged). BBP assumes these hardware components are functional and accessible via the device's operating system APIs.

\subsection{Software interfaces}
\label{subsec:software_interfaces}%
BBP will interact with several other software entities. A critical interface exists with the mobile device's Operating System (OS). Through OS APIs, BBP must request and manage permissions for accessing hardware sensors (GPS, accelerometer, gyroscope), handle background execution for continuous trip recording, potentially manage local storage for application data, and interact with network services. Another vital software interface is with the External Weather Service. BBP must communicate with this external service via its provided Application Programming Interface (API), likely transmitting location coordinates (and potentially time information) and receiving structured weather forecast data (e.g., in JSON format) containing temperature, wind speed, precipitation probability, and general conditions . The specific protocol and data format will be dictated by the chosen weather service provider. 

\subsection{Communication interfaces}
\label{subsec:communication_interfaces}%

The BBP system inherently requires network connectivity for many of its core functions. An active internet connection, typically via cellular data (e.g., 4G, 5G) or Wi-Fi, is necessary for user authentication (signup/login), searching for public paths, retrieving path details (including merged status and reports) , fetching real-time weather data from the external service , and saving or publishing user-generated trips and reports. Communication with the BBP backend server (which manages user accounts, paths, reports, etc.) will occur over standard secure web protocols(HTTPS), to ensure data integrity and confidentiality during transit. BBP must gracefully handle temporary losses of connectivity where possible, although core online features will be unavailable without an active connection (as per DA12).

\section{Performance requirements}%faccio io qui ( Bellosi)
\label{sec:performance_requirements}%
This section specifies the non-functional requirements related to system response time,
concurrent user load, data storage capacity, and data acquisition timing constraints.

% Use the 'enumerate' environment for automatic numbering (PR-1, PR-2, etc.)
% 'enumitem' package is recommended (include \usepackage{enumitem} in your preamble)
% 'label=\textbf{PR-\arabic*.}' sets the format
% 'leftmargin=*' aligns the list properly
% 'itemsep=2pt' adds a small space between items
\begin{enumerate}[label=\textbf{PR-\arabic*.}, leftmargin=*, itemsep=2pt]

    \item \textbf{(Time response: Login):} The system shall authenticate a \texttt{RCY} (Registered Cyclist) (R3) and display the main map screen within \textbf{2.0 seconds} of the login submission.
    
    \item \textbf{(Time response: Search):} The system shall process a \texttt{Search paths} request (R7), including retrieving reports (R8), executing merging logic (R9), calculating scores (R10), fetching weather data (R14), and displaying the ordered results list (R11) within \textbf{5.0 seconds}.
    
    \item \textbf{(Time response: View Details):} The system shall display the full \texttt{View path details} screen (R13), including geometry, merged status, obstacles, and weather (R14), within \textbf{3.0 seconds} of the user's selection (R12).
    
    \item \textbf{(Time response: Start Recording):} The \texttt{Record trip (automatic)} session (R20) must initialize and begin active monitoring of sensors (R21, R23) within \textbf{1.5 seconds} of the user tapping "Start".
    
    \item \textbf{(Time response: Sensor Frequency):} During an \textbf{active} recording state (R20):
    \begin{itemize}[leftmargin=*, noitemsep, nolistsep]
        \item The GPS (R21) must be sampled at a minimum frequency of \textbf{1 Hz} (one sample per second) to ensure accurate geometry.
        \item The Accelerometer and Gyroscope (R23) must be sampled at a minimum frequency of \textbf{10 Hz} (ten samples per second) to reliably capture data for pothole detection (R24).
    \end{itemize}
    
    \item \textbf{(Time response: Save):} The system shall complete the server-side save operation for a \texttt{Trip} (R33) and/or \texttt{Path} (R25), including persisting the selected visibility options (R39) and the stored visibility settings (R25, R26), and return a confirmation message (R40) within \textbf{4.0 seconds} of the user tapping "Save".
    
    \item \textbf{(Number of concurrent users: General):} The BBP backend shall support a minimum of \textbf{1,000 concurrent users} (ACY and RCY) performing searches (R7) or navigation (R15) without degrading the response times defined in PR-2 and PR-3.
    
    \item \textbf{(Number of concurrent users: Recording):} The system shall support at least \textbf{50 concurrent \texttt{Record trip (automatic)}} sessions (R20) being initiated per minute.
    
    \item \textbf{(Data storage: Scalability):} The system architecture must be scalable to support the storage and processing (R8, R9) of an average of \textbf{10,000 new \texttt{Trip}s} and \textbf{50,000 new \texttt{Report}s} per day.
    
    \item \textbf{(Data storage: Retention):} All user-generated \texttt{Trip} data (R33),including final statistics (R31) and associated weather information (R32), \texttt{Path} data (R25), and \texttt{Report} data (R37, R38) shall be retained indefinitely.

    \item \textbf{(Time response: Stop Recording):} After the user taps "Stop Recording" (R27), BBP shall stop sensor acquisition and display the post-recording screen (Review Detections if \texttt{sensor\_event}s were logged (R28), otherwise the Trip summary) within \textbf{3 seconds}.
\end{enumerate}

\section{Design constraints}
\label{sec:design_constraints}%
This section outlines specific constraints that restrict the design and implementation choices for the BBP system.

\subsection{Standard compliance}
\label{subsec:standard compliance}%%
\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Web Communication:} All communication between the BBP mobile application and the BBP backend server must use secure, standard protocols, specifically \textbf{HTTPS}.
    \item \textbf{Data Interchange:} Data interchange with all external services, particularly the \texttt{External Weather Service}, must adhere to standard data formats, primarily \textbf{JSON}.
    \item \textbf{Data Privacy:} As the system collects and stores sensitive user data, including personal information (R1, R2) and precise location history (R21, R33), the design must comply with relevant data protection regulations, such as the \textbf{GDPR}.
\end{itemize}

\subsection{Hardware limitations}
\label{subsec:hardware_limitations}%
\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Device Type:} The system is constrained to run on consumer smartphones (e.g., iOS and Android) .
    \item \textbf{Required Sensors:} All core functionalities for automatic recording (R20, R23) are strictly dependent on the availability and user-granted permission for specific hardware sensors: \textbf{GPS}, \textbf{Accelerometer}, and \textbf{Gyroscope}. Devices lacking these sensors will be limited to manual path creation (R36) and search/navigation (R7, R15).
    \item \textbf{Connectivity:} The system is not designed for full offline operation. An active internet connection (Wi-Fi or cellular data) is a constraint for most core functions, including login (R3), search (R7), submitting Reports (R31, R38)and saving/publishing Trips and Paths (R33, R25, R39) with stored visibility rules (R25, R26).
\end{itemize}

\subsubsection{Any other constraint}
\label{subsec:Any other constraint}%
\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Platform Type:} The user interface must be implemented as a \textbf{native mobile application} to ensure reliable access to background processes and hardware sensors (GPS, IMU) . A web-based application is not sufficient to meet the core functional requirements (R20, R23).
    \item \textbf{External API Dependency:} The system is constrained by its dependency on third-party services. The \texttt{External Weather Service} (R14, R32)  and any underlying map provider (e.g., Google Maps, OpenStreetMap) are external dependencies. The design must be resilient to their potential downtime or API changes.
    \item \textbf{Architecture:} The requirement for server-side aggregation (R8, R9) and scoring (R10) constrains the system to a \textbf{Client-Server architecture}. A purely peer-to-peer or standalone application is not feasible.
\end{itemize}

\section{Software system attributes}
\label{sec:software_system_attributes}%
This section defines the key quality attributes (non-functional requirements) that the BBP system must exhibit.

\subsection{Reliability}
\label{subsec:reliability}%
The system must demonstrate high reliability during its core operations.
\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Recording Stability:} The \texttt{Record trip (automatic)} session (R20) must be robust. The application must be able to handle continuous background data streams from GPS (R21) and IMU sensors (R23) for extended periods (e.g., up to 3 hours) without crashing or corrupting data.
    \item \textbf{Data Integrity (Sensors):} The system must reliably process sensor data (R23) to ensure that \texttt{sensor\_event} logs (R24) are correctly generated based on the defined thresholds (DA4) and are not lost, even if the application is temporarily suspended.
    \item \textbf{Data Integrity (Save):} The system must ensure that a "Save" operation (Trip save: R33; Path save: R25; visibility selection: R39; stored visibility settings: R25, R26) is atomic. A failure during saving (e.g., network loss) must not result in partially saved or corrupted \texttt{Trip} or \texttt{Path} data.
\end{itemize}

\subsection{Availability}
\label{subsec:availability}%
The server-side components of the BBP system must be highly available.
\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Core Service Uptime:} All backend services responsible for user authentication (R3), path searching (R7), and data aggregation (R8, R9, R10) shall maintain an availability of \textbf{99.5\%} (Tier 3 equivalent).
    \item \textbf{Graceful Degradation:} In the event of an \texttt{External Weather Service} (R14, R32) outage, the system shall remain available, displaying path and trip details without weather data and notifying the user of the temporary unavailability.
\end{itemize}

\subsection{Security}
\label{subsec:security}%
The system must protect the integrity and confidentiality of user data.
\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Data in Transit:} All communication between the BBP Application and the BBP Server must be encrypted using \textbf{HTTPS}.
    \item \textbf{Authentication:} User passwords must be stored on the server using a strong, salted, one-way hashing algorithm.
    \item \textbf{Authorization:} The system must enforce strict data access controls. A \texttt{RegisteredUser} must only be able to view their own private \texttt{Trip} data (R33), enforced by the trip visibility rules (R26), via the saved trips list/details features (R34, R35). Data associated with other users must not be accessible.
    \item \textbf{Data Privacy (Location):} User GPS data (R21), both in transit and at rest, must be treated as sensitive personal information and protected against unauthorized access.
\end{itemize}

\subsection{Maintainability}
\label{subsec:maintainability}%
The system must be designed to be easily modified and maintained.
\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Modularity (Scoring):} The logic for \texttt{Path} scoring (R10) and \texttt{Report} merging (R9) must be implemented in a distinct, loosely-coupled module on the server. This allows the aggregation algorithm to be tuned or replaced without impacting core trip recording or user management functionalities.
    \item \textbf{Modularity (Detection):} The algorithm for processing raw sensor data (R23) into \texttt{sensor\_event}s (R24) must be isolated within the client application, allowing the detection thresholds (DA4) to be updated or calibrated without requiring a full application rewrite.
\end{itemize}

\subsection{Portability}
\label{subsec:portability}%
\begin{itemize}[leftmargin=*, itemsep=2pt]
    \item \textbf{Client Platform:} The BBP mobile application shall be designed to be portable across the two primary mobile operating systems: \textbf{iOS} and \textbf{Android}.
    \item \textbf{OS Dependencies:} The design must account for differences in OS-level APIs (e.g., for accessing sensor data (R23) and managing background processes (R20)), ensuring functionally equivalent behavior on both platforms.
\end{itemize}
