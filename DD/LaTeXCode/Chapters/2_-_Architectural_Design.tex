\section{Overview}
\label{sec:Overview}
Here we represents an overview of how the entire BBP architecture is composed of:

\begin{figure}[H]
    \begin{center}
        \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/overview/overview.png}
        \caption{BBP Overview.}
        \label{fig:BBP_overview}%
    \end{center}
\end{figure}
\noindent Client Side:
\begin{itemize}
    \item \textbf{Mobile Client (iOS/Android):} Serves as the primary User Interface (UI) and data collection tool. It provides the native screens for all user interactions, runs a persistent foreground service to continuously capture data from device sensors (GPS, accelerometer, gyroscope), and manages the post-ride summary screen for reviewing events and setting visibility preferences.
\end{itemize}

\noindent Server Side:
\begin{itemize}
    \item \textbf{Backend Server (API \& Core Logic):} Handles all business logic, data integrity, and security via a secure REST API. It processes all incoming data from the client (e.g., saving new trips and paths atomically), manages user authentication, and performs complex server-side operations like aggregating trip statistics to update path averages. It is the single source of truth for all data.
    
    \item \textbf{BBP Database (PostgreSQL + PostGIS):} Stores all data related to users, paths, trips, and reports. It utilizes PostgreSQL for relational data and the \textbf{PostGIS} extension to efficiently store and query all geospatial data (e.g., path geometries, obstacle locations), enabling the core path-searching functionality.
    
    \item \textbf{Device Sensors (GPS, Accelerometer, Gyroscope):} Provides the raw hardware-level data streams to the Mobile Client. The GPS is used to build the trip's geometry, while the \textbf{Accelerometer} and \textbf{Gyroscope} provide motion data used to automatically detect potential obstacles (e.g., potholes).
    
    \item \textbf{External Weather Service:} Utilized by the Backend Server to fetch meteorological data. When a trip is saved, the server queries this API to retrieve weather conditions (e.g., temperature, wind speed) for the trip's time and location, adding valuable context to the user's log.
    
    \item \textbf{External Navigation Service:} Invoked by the Mobile Client to provide turn-by-turn directions. When a user "Follows Path," the client sends the route's destination or geometry to the device's default mapping application, allowing BBP to focus on its core recording and evaluation features.
\end{itemize}

\subsection{High Level Diagram}

This diagram defines the high-level system boundaries and the primary components of the Best Bike Paths (BBP) system. It illustrates a classic client-server architecture, clearly separating the client-side data collection components from the server-side business logic and persistence components.



\noindent \textbf{Mobile App} \\
Serves as the external access point for users and the primary data collection tool. It allows communication with the \texttt{BBP backend server} through the \texttt{BBP API}, which is the sole interface for all server-side business logic (like searching paths and saving trips). The \texttt{Mobile App} also requires raw data from the \texttt{Device sensor} component via the \texttt{Device info} interface for live recording and triggers the \texttt{External navigation service} using the \texttt{Navigation service} interface.

\vspace{0.5em} % Aggiunge un po' di spazio tra i paragrafi

\noindent \textbf{BBP backend server} \\
Serves as the central authority for all business logic, security, and persistence. It \textit{provides} the \texttt{BBP API} to handle all incoming requests from the \texttt{Mobile App}. To fulfill these requests, it requires access to the \texttt{BBP Database} through the \texttt{DBMS API} for all data storage, and also queries the \texttt{External weather service} via the \texttt{Weather info API} to enrich trip data.

\vspace{0.5em}

\noindent \textbf{Device sensor} \\
Acts as the hardware-level data provider, representing the phone's GPS, accelerometer, and gyroscope. It \textit{provides} the \texttt{Device info} interface, which is consumed exclusively by the \texttt{Mobile App} to stream the raw location and motion data necessary for trip recording.

\vspace{0.5em}

\noindent \textbf{External navigation service} \\
A third-party mapping application (e.g., Google Maps) that \textit{provides} the \texttt{Navigation service} interface (e.g., an OS-level Intent or URL scheme). It is triggered by the \texttt{Mobile App} to launch and provide the user with turn-by-turn directions.

\vspace{0.5em}

\noindent \textbf{BBP Database} \\
The system's core persistence component, utilizing PostgreSQL and PostGIS. It \textit{provides} the \texttt{DBMS API}, which is consumed exclusively by the \texttt{BBP backend server} to store and retrieve all application data, including user accounts, paths, trips, and geospatial tracks.

\vspace{0.5em}

\noindent \textbf{External weather service} \\
A third-party data provider that \textit{provides} the \texttt{Weather info API}. This interface is consumed by the \texttt{BBP backend server} (and \textit{not} the client) to fetch meteorological data, such as temperature and wind conditions, when a new trip is saved.

This section details the internal components of the primary system packages: the \texttt{Mobile App} and the \texttt{BBP backend server}. This view illustrates the internal logic and sub-component responsibilities required to implement the system's functionalities.

\subsection*{Mobile App (Client) Component Descriptions}
\vspace{0.5em}
\noindent \textbf{UI layer} \\
Serves as the central orchestrator for all user interactions. It \textit{consumes} (requires) interfaces from multiple services to function: it \textit{consumes} the \texttt{HUD interface} (from \texttt{recording service}) to display live stats, the \texttt{Saved data interface} (from \texttt{Local storage}) to retrieve tokens/cache, and the \texttt{connection interface} (from \texttt{Network layer}) to display network status. It \textit{provides} (controls) interfaces to command other components: \texttt{Start recording interface} (for \texttt{recording service}), \texttt{Navigation interface} (for \texttt{navigation manager}), and \texttt{Saving interface} (for \texttt{Local storage}).

\vspace{0.5em}
\noindent \textbf{sensor manager} \\
This component abstracts the physical hardware. It \textit{consumes} (requires) the \texttt{sensor info} interface provided by the external \texttt{Device sensor} and \textit{provides} a clean data stream interface that is consumed by the \texttt{recording service}.

\vspace{0.5em}
\noindent \textbf{recording service} \\
The core of the trip/path recording functionality. It \textit{consumes} (requires) the \texttt{Start recording interface} (from \texttt{UI layer}) and the data interface (from \texttt{sensor manager}). It \textit{provides} two interfaces: the \texttt{HUD interface} (consumed by \texttt{UI layer}) and a \texttt{Saving interface} (consumed by \texttt{Network layer} and \texttt{Local storage}) to pass on the completed trip/path data.

\vspace{0.5em}
\noindent \textbf{navigation manager} \\
Manages the external navigation functionality (UC6). It \textit{consumes} (requires) the \texttt{Navigation interface} (from \texttt{UI layer}) and the \texttt{connection interface} (from \texttt{Network layer}). It then \textit{consumes} (requires) the external \texttt{Navigation service} interface (from the external app).

\vspace{0.5em}
\noindent \textbf{Network layer} \\
Handles all communication with the backend. It \textit{consumes} (requires) the \texttt{BBP API} (provided by the \texttt{Controller layer}). It also \textit{consumes} \texttt{Saving interfaces} (from \texttt{recording service} and \texttt{Local storage}) to get the data to send. It \textit{provides} the \texttt{connection interface} to the \texttt{UI layer} and \texttt{navigation manager}.

\vspace{0.5em}
\noindent \textbf{Local storage} \\
Manages on-device persistence. It \textit{provides} the \texttt{Saved data interface} consumed by the \texttt{UI layer}, \texttt{Network layer} and \textit{recording service}.

\subsection*{BBP backend server Component Descriptions}

\vspace{0.5em}
\noindent \textbf{Controller layer} \\
The single entry point for all client requests. It \textit{provides} the \texttt{BBP API} that the client's \texttt{Network layer} consumes. It \textit{consumes} (requires) the \texttt{Security interface} (to validate requests) and the \texttt{authentication interface} (for public login/register routes).

\vspace{0.5em}
\noindent \textbf{Security module} \\
Acts as the central authorization gate. It \textit{provides} the \texttt{Security interface} (consumed by the \texttt{Controller layer}). It \textit{consumes} (requires) interfaces from \texttt{Auth service} (to validate tokens), \texttt{Path service}, \texttt{Trip service}, and \texttt{Profile manager} to forward authorized requests.

\vspace{0.5em}
\noindent \textbf{Auth service} \\
Manages user identity (UC1, UC2). It \textit{provides} the \texttt{authentication interface} (consumed by the \texttt{Controller layer}). It \textit{consumes} (requires) the \texttt{Model interface} to find/create users in the database, also provide the token verification in case of logged user.

\vspace{0.5em}
\noindent \textbf{Profile manager} \\
Manages user-specific data (e.g., name, email). It \textit{consumes} (requires) an interface from the \texttt{Security module} and also \textit{consumes} (requires) the \texttt{Model interface} to update or fetch profile data.

\vspace{0.5em}
\noindent \textbf{Path service} \\
Handles all logic related to paths (UC4, UC5). It \textit{consumes} (requires) an interface from the \texttt{Security module}. It \textit{consumes} (requires) the \texttt{Model interface} for all path-related database queries, and it also \textit{consumes} (requires) the \texttt{Weather interface} (provided by the \texttt{Weather API client}) to fetch *forecast* data (R14).

\vspace{0.5em}
\noindent \textbf{Trip service} \\
Handles all logic related to individual trips (UC9, UC13). It \textit{consumes} (requires) an interface from the \texttt{Security module}. It \textit{consumes} (requires) the \texttt{Model interface} to save or retrieve trip data. It also \textit{consumes} (requires) the \texttt{Weather interface} (red line) to fetch a *historical snapshot* of the weather (R32).

\vspace{0.5em}
\noindent \textbf{Model} \\
The data access façade (Repository Pattern). It \textit{provides} the central \texttt{Model interface} that all services (\texttt{Auth}, \texttt{Profile}, \texttt{Path}, \texttt{Trip}) consume. It, in turn, \textit{consumes} (requires) the \texttt{DBMS API} provided by the \texttt{BBP Database}.

\vspace{0.5em}
\noindent \textbf{Weather API client} \\
A specialized wrapper for the external weather service. It \textit{provides} the \texttt{Weather interface} that is consumed by both the \texttt{Path service} and \texttt{Trip service}. It translates these internal requests by \textit{consuming} (requiring) the external \texttt{Weather info API}.


\subsubsection{CMP: Path service}
\label{sec:cmp_path_service}

\begin{figure}[H]
    \begin{center}
        \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/componentDiagrams/Component_diagram-path_detailed_view.drawio.png}
        \caption{Path service}
        \label{fig:Path service}%
    \end{center}
\end{figure}

This component manages all business logic related to the creation, searching, and viewing of \texttt{Paths}. It consumes the \texttt{Model interface} for all database operations and the \texttt{Weather interface} for forecasts. The component exposes a single \texttt{Path interface} port to the \texttt{Security module}, which internally routes to three specialized interfaces.

\vspace{0.5em}
\noindent \textbf{path adding} \\
Handles the logic for manually creating a new \texttt{Path} (UC11). It \textit{consumes} (requires) the \texttt{Path adding interface} to receive data. To persist the new \texttt{Path} entity, it \textit{consumes} (requires) the \texttt{Model interface}.

\vspace{0.5em}
\noindent \textbf{Path searcher} \\
Handles the primary search functionality (UC4). It \textit{consumes} (requires) the \texttt{Search path interface}. It implements the \textit{On-Read} (lazy) aggregation logic by consuming two interfaces:
\begin{itemize}
    \item The \texttt{Model interface}: to retrieve \texttt{Paths}, associated \texttt{Trips} (for live statistics calculation), and \texttt{Reports}.
    \item The \texttt{Path merger interface}: to calculate the "fresh" status from the retrieved reports.
\end{itemize}

\vspace{0.5em}
\noindent \textbf{Detailed path view} \\
Handles the logic for fetching a single, detailed \texttt{Path} (UC5). It \textit{consumes} (requires) the \texttt{Detailed path interface}. This is the most complex read operation, as it \textit{consumes} (requires) three distinct interfaces to build the final view:
\begin{itemize}
    \item The \texttt{Model interface}: for all core path, trip, and report data.
    \item The \texttt{Path merger interface}: for the "fresh" status.
    \item The \texttt{Weather interface}: to fetch the current weather forecast for the path's location (R14).
\end{itemize}

\vspace{0.5em}
\noindent \textbf{Path merger} \\
This is an internal "worker" module that implements the \textit{On-Read} logic for calculating the path status (R9). It \textit{provides} the \texttt{Path merger interface} (consumed by \texttt{Path searcher} and \texttt{Detailed path view}). To perform its calculation, it \textit{consumes} (requires) the \texttt{Model interface} to retrieve the necessary \texttt{Status\_reports}.

\subsubsection{CMP: Trip service}
\label{sec:cmp_trip_service}

\begin{figure}[H]
    \begin{center}
        \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/componentDiagrams/Component_diagram-Trip_detailed_view.drawio.png}
        \caption{Trip service}
        \label{fig:Trip service}%
    \end{center}
\end{figure}
This component is responsible for all business logic related to individual \texttt{Trips}, including their creation and retrieval. It exposes a single facade interface (the \texttt{Trip interface}) to the \texttt{Security module}, which internally routes requests to two specialized modules.

\vspace{0.5em}
\noindent \textbf{trip adding} \\
This module handles the complex orchestration of saving a new \texttt{Trip}. After being triggered by the facade, it \textit{consumes} (requires) two critical interfaces:
\begin{itemize}
    \item The \texttt{Weather interface} (from the \texttt{Weather API client}) to fetch a the  snapshot of the weather conditions of the trip (R32).
    \item The \texttt{Model interface} (from the \texttt{Model}) to atomically save the new \texttt{Trip}, its \texttt{Path}, and any confirmed \texttt{Reports} to the database (R33).
\end{itemize}

\vspace{0.5em}
\noindent \textbf{trip searcher} \\
This module handles the retrieval of a user's personal trip history (UC13). It is a simple read operation that, once triggered by the facade, \textit{consumes} (requires) the \texttt{Model interface} to fetch the list of \texttt{Trips} associated with the user's ID.

\subsubsection{CMP: Auth service}
\label{sec:cmp_auth_service}
\begin{figure}[H]
    \begin{center}
        \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/componentDiagrams/Component_diagram-Auth_detailed_view.drawio.png}
        \caption{Auth service}

This component manages all logic for user identity (UC1, UC2). It provides the core services for user registration and login, which are triggered by the \texttt{Controller layer} (bypassing the \texttt{Security module} for public routes). It also provides the critical token validation interface consumed by the \texttt{Security module} for all authenticated requests.

\vspace{0.5em}
\noindent \textbf{user service} \\
This is the central orchestrator for authentication logic, containing the business logic for both registration and login. It \textit{consumes} (requires) interfaces from three specialized "worker" modules to execute its tasks:
\begin{itemize}
    \item The interface \textit{provided} by \textbf{Hash password} (to hash new passwords and verify existing ones).
    \item The interface \textit{provided} by \textbf{token manager} (to generate new session tokens upon successful login).
    \item The \texttt{Model interface} \textit{provided} by the external \textbf{Model} (to find, create, and save user data in the database).
\end{itemize}

\subsubsection{CMP: Recording service}
\label{sec:cmp_recording_service}

This component package contains the core client-side logic for the trip recording functionality (UC7). It is managed by an internal \texttt{Recording state manager} that orchestrates several sub-modules. It receives commands from the \texttt{UI layer} and raw data from the \texttt{sensor manager}.

\vspace{0.5em}
\noindent \textbf{Recording state manager} \\
This is the central orchestrator of the service. It \textit{consumes} (requires) two interfaces: one from the \texttt{UI layer} (to receive commands like start/stop) and one from the \texttt{sensor manager} (to receive the raw data stream). It \textit{provides} (controls) three interfaces: one back to the \texttt{UI layer} (to send HUD updates), one to the \texttt{GPS tracker}, and one to the \texttt{Sensor processor} (likely to command them to start/stop processing).

\vspace{0.5em}
\noindent \textbf{Stats tracker} \\
This module is responsible for calculating real-time statistics (R22). It \textit{consumes} (requires) two interfaces: one from the \texttt{UI layer} (e.g., to receive reset/start commands) and one from the \texttt{GPS tracker} (to receive the position data needed to calculate distance and speed).

\vspace{0.5em}
\noindent \textbf{GPS tracker} \\
This module's sole responsibility is managing the GPS data. It \textit{consumes} (requires) a command interface from the \texttt{Recording state manager} and \textit{provides} a data interface (the stream of \texttt{GPS\_points}) that is consumed by the \texttt{Stats tracker}.

\vspace{0.5em}
\noindent \textbf{Sensor processor} \\
This module is responsible for analyzing the motion sensor data (R24). It \textit{consumes} (requires) a command interface from the \texttt{Recording state manager}. It \textit{provides} an interface (likely with the detected \texttt{sensor\_events}) that is consumed directly by the \texttt{Local storage} component for caching.
