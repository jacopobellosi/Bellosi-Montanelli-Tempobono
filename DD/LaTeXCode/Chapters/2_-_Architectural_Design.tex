\section{Overview}
\label{sec:Overview}
Here we represents an overview of how the entire BBP architecture is composed of:

\begin{figure}[H]
    \begin{center}
        \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/overview/overview.png}
        \caption{BBP Overview.}
        \label{fig:BBP_overview}%
    \end{center}
\end{figure}
\noindent Client Side:
\begin{itemize}
    \item \textbf{Mobile Client (iOS/Android):} Serves as the primary User Interface (UI) and data collection tool. It provides the native screens for all user interactions, runs a persistent foreground service to continuously capture data from device sensors (GPS, accelerometer, gyroscope), and manages the post-ride summary screen for reviewing events and setting visibility preferences.
\end{itemize}

\noindent Server Side:
\begin{itemize}
    \item \textbf{Backend Server (API \& Core Logic):} Handles all business logic, data integrity, and security via a secure REST API. It processes all incoming data from the client (e.g., saving new trips and paths atomically), manages user authentication, and performs complex server-side operations like aggregating trip statistics to update path averages. It is the single source of truth for all data.
    
    \item \textbf{BBP Database (PostgreSQL + PostGIS):} Stores all data related to users, paths, trips, and reports. It utilizes PostgreSQL for relational data and the \textbf{PostGIS} extension to efficiently store and query all geospatial data (e.g., path geometries, obstacle locations), enabling the core path-searching functionality.
    
    \item \textbf{Device Sensors (GPS, Accelerometer, Gyroscope):} Provides the raw hardware-level data streams to the Mobile Client. The GPS is used to build the trip's geometry, while the \textbf{Accelerometer} and \textbf{Gyroscope} provide motion data used to automatically detect potential obstacles (e.g., potholes).
    
    \item \textbf{External Weather Service:} Utilized by the Backend Server to fetch meteorological data. When a trip is saved, the server queries this API to retrieve weather conditions (e.g., temperature, wind speed) for the trip's time and location, adding valuable context to the user's log.
    
    \item \textbf{External Navigation Service:} Invoked by the Mobile Client to provide turn-by-turn directions. When a user "Follows Path," the client sends the route's destination or geometry to the device's default mapping application, allowing BBP to focus on its core recording and evaluation features.
\end{itemize}

This diagram defines the high-level system boundaries and the primary components of the Best Bike Paths (BBP) system. It illustrates a classic client-server architecture, clearly separating the client-side data collection components from the server-side business logic and persistence components.



\noindent \textbf{Mobile App} \\
Serves as the external access point for users and the primary data collection tool. It allows communication with the \texttt{BBP backend server} through the \texttt{BBP API}, which is the sole interface for all server-side business logic (like searching paths and saving trips). The \texttt{Mobile App} also requires raw data from the \texttt{Device sensor} component via the \texttt{Device info} interface for live recording and triggers the \texttt{External navigation service} using the \texttt{Navigation service} interface.

\vspace{0.5em} % Aggiunge un po' di spazio tra i paragrafi

\noindent \textbf{BBP backend server} \\
Serves as the central authority for all business logic, security, and persistence. It \textit{provides} the \texttt{BBP API} to handle all incoming requests from the \texttt{Mobile App}. To fulfill these requests, it requires access to the \texttt{BBP Database} through the \texttt{DBMS API} for all data storage, and also queries the \texttt{External weather service} via the \texttt{Weather info API} to enrich trip data.

\vspace{0.5em}

\noindent \textbf{Device sensor} \\
Acts as the hardware-level data provider, representing the phone's GPS, accelerometer, and gyroscope. It \textit{provides} the \texttt{Device info} interface, which is consumed exclusively by the \texttt{Mobile App} to stream the raw location and motion data necessary for trip recording.

\vspace{0.5em}

\noindent \textbf{External navigation service} \\
A third-party mapping application (e.g., Google Maps) that \textit{provides} the \texttt{Navigation service} interface (e.g., an OS-level Intent or URL scheme). It is triggered by the \texttt{Mobile App} to launch and provide the user with turn-by-turn directions.

\vspace{0.5em}

\noindent \textbf{BBP Database} \\
The system's core persistence component, utilizing PostgreSQL and PostGIS. It \textit{provides} the \texttt{DBMS API}, which is consumed exclusively by the \texttt{BBP backend server} to store and retrieve all application data, including user accounts, paths, trips, and geospatial tracks.

\vspace{0.5em}

\noindent \textbf{External weather service} \\
A third-party data provider that \textit{provides} the \texttt{Weather info API}. This interface is consumed by the \texttt{BBP backend server} (and \textit{not} the client) to fetch meteorological data, such as temperature and wind conditions, when a new trip is saved.

\subsection{Mobile App Components}

\begin{itemize}
    \item \textbf{UI layer}: This component serves as the primary interface for user interaction. It is responsible for rendering the application's visual elements, managing the navigational flow between different screens, and capturing user inputs. It orchestrates the presentation of real-time data, such as maps and recording statistics, ensuring a responsive user experience.

    \item \textbf{sensor manager}: This component acts as a hardware abstraction layer. Its primary function is to interface directly with the device's physical sensors (GPS, accelerometer, and gyroscope). It handles the acquisition of raw telemetry data and normalizes these signals for internal processing.

    \item \textbf{recording service}: This component encapsulates the core business logic for the automatic path recording feature. Operating as a background process, it is responsible for tracking the user's movement, calculating real-time session statistics (e.g., speed, distance, duration), and analyzing sensor data to detect significant physical events, such as potholes.

    \item \textbf{navigation manager}: This component is responsible for facilitating the navigation experience. It manages the logic required to initiate turn-by-turn directions, handling the preparation of route geometry and the invocation of external navigation capabilities provided by the operating system.

    \item \textbf{Network layer}: This component manages all remote data transmission. It is responsible for serializing domain objects into JSON format, constructing HTTP requests, and handling network responses. It ensures that all communication with the remote server adheres to the defined API protocols.

    \item \textbf{Local storage}: This component provides a persistence mechanism within the mobile device. It is tasked with securely storing sensitive session information, such as authentication tokens, and caching temporary data—including draft paths and recording sessions—to ensure data integrity and availability during offline scenarios.
\end{itemize}

\subsection{BBP Backend Server Components}

\begin{itemize}
    \item \textbf{Controller layer}: This component serves as the entry point for the backend system. It is responsible for exposing the RESTful API endpoints, receiving incoming HTTP requests, and performing initial validation of the input data before delegating the processing to the appropriate internal logic, it also check the validity of the request ensuring only the authorized users can access.


    \item \textbf{Auth service}: This component encapsulates the logic regarding user identity management. It handles the critical processes of registering new accounts, verifying user credentials during login attempts, and generating secure session tokens for authenticated users.

    \item \textbf{Profile manager}: This component is dedicated to the administration of user-specific data. It handles operations related to the retrieval and modification of personal profile information, ensuring that user preferences and account details are accurately maintained.

    \item \textbf{Path service}: This component contains the domain logic associated with cycling paths. It is responsible for executing search algorithms based on geospatial criteria, computing path scores based on community feedback, and processing detailed path information for display.

    \item \textbf{Trip service}: This component manages the lifecycle of individual user trips. Its functions include the processing and persistence of recorded cycling sessions, the logical association of trips with specific paths, and the retrieval of a user's personal activity history.

    \item \textbf{Model}: This component serves as the Data Access Layer (DAL), implementing the Repository pattern. It is responsible for abstracting the underlying database technology, translating high-level domain operations into specific queries to persist, update, and retrieve relational and geospatial data.

    \item \textbf{Weather API client}: This component acts as a gateway to external meteorological services. It is responsible for formulating requests to third-party APIs to retrieve current weather conditions or forecasts and for parsing the external response data into a format usable by the internal system.
\end{itemize}




\subsubsection{CMP: Path service}
\label{sec:cmp_path_service}

\begin{figure}[H]
    \begin{center}
        \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/componentDiagrams/Component_diagram-path_detailed_view.drawio.png}
        \caption{Path service}
        \label{fig:Path service}%
    \end{center}
\end{figure}

The \texttt{Path service} component is the centralized unit responsible for all operations concerning cycling paths. It functions as a facade that presents a unified \texttt{Path interface} to the external \texttt{Security module}, while internally delegating distinct tasks to a collection of dedicated sub-components. This internal design guarantees a well-defined separation of responsibilities for path creation, lookup, and modification.
\begin{itemize}
    \item \textbf{Path adding}: This sub-component manages the persistence of new path entities. It is invoked when a user finalises a path-creation process (e.g., during a manual save operation). Its primary function is to validate the geometric and metadata integrity of the new path and coordinate its storage by communicating with the \texttt{Model} via the \texttt{Model interface}.

    \item \textbf{Path searcher}: This sub-component is responsible for the execution of search queries. It processes criteria provided by the user (such as origin and destination), interacts with the \texttt{Model} to perform geospatial queries, and retrieves the set of relevant path candidates.

    \item \textbf{Detailed path view}: This sub-component handles the retrieval and aggregation of comprehensive information for a specific path. It orchestrates data collection from multiple sources: it fetches static path data from the \texttt{Model}, requests current status calculations from the \texttt{Path merger}, and retrieves real-time weather forecasts by invoking the external \texttt{Weather API client}.

    \item \textbf{Path merger}: This sub-component serves as a stateless calculation engine. Its function is to compute the dynamic status of a path (e.g., "Optimal" vs "Requires Maintenance") by aggregating historical user reports. It applies specific business rules, such as freshness and majority voting, to derive a definitive status without directly persisting data.

    \item \textbf{Add status to path}: This sub-component manages the submission of general condition reports. When a user provides feedback on a path's status, this module processes the input and delegates the persistence of the new status report to the \texttt{Model}.

    \item \textbf{Add obstacle to path}: This sub-component handles the reporting of specific hazards. It processes user submissions regarding obstacles (e.g., type and location) and ensures these critical safety updates are recorded in the system via the \texttt{Model}.
\end{itemize}

\subsubsection{CMP: Trip service}
\label{sec:cmp_trip_service}

\noindent This component is responsible for all business logic related to individual \texttt{Trips}, including their creation (UC9) and retrieval (UC13). It exposes a single facade port to the \texttt{Security module}, which internally routes requests to two specialized interfaces: \texttt{Trip adding interface} and \texttt{Trip search interface}.

\begin{itemize}
    \item \textbf{path adding}: This component is responsible for the persistence of new path entities into the system. It handles the validation of geometric data and metadata provided by the user (such as during manual path creation) and coordinates the transactional storage of this information within the database.

    \item \textbf{Path searcher}: This component encapsulates the logic for path discovery. Its primary function is to process user-defined search criteria (e.g., origin and destination coordinates) and execute complex geospatial queries to identify relevant routes. It also coordinates with the aggregation logic to ensure that the returned search results reflect the current computed status of each path.

    \item \textbf{Detailed path view}: This component acts as a data aggregator for the presentation layer. Its function is to compile a comprehensive snapshot of a specific path by synthesizing heterogeneous data sources: it retrieves static geometric data, requests the computation of the dynamic path status, and fetches real-time meteorological forecasts to provide the user with a complete contextual overview.

    \item \textbf{Path merger}: This component serves as a stateless calculation engine implementing the system's consensus algorithms. It is responsible for processing the history of user-submitted reports to derive a definitive "Path Status" (e.g., "Optimal", "Requires Maintenance"). It applies specific business rules regarding data freshness and majority voting to filter noise and determine the current condition of a route without modifying the persistent state directly.

    \item \textbf{Add status to path}: This component manages the submission of general condition ratings. It is responsible for processing user feedback regarding the overall quality of a path, ensuring that these subjective assessments are correctly structured and persisted as \texttt{Status\_reports} for future aggregation.

    \item \textbf{Add obstacle to path}: This component handles the reporting of specific physical hazards. It is tasked with processing geospatial submissions regarding obstacles (e.g., potholes, roadworks), validating the input location, and persisting these critical safety warnings as \texttt{Obstacle\_reports}.
\end{itemize}

\subsubsection{CMP: Auth service}
\label{sec:cmp_auth_service}

The \texttt{Auth service} component constitutes the authoritative domain boundary for identity and access management within the system. It acts as a comprehensive security provider, encapsulating the logic required to establish, verify, and maintain user identities throughout their lifecycle, ensuring that all access to the system is strictly authenticated.

\begin{itemize}
    \item \textbf{User service}: This sub-component serves as the central orchestrator for authentication workflows. It implements the core business rules for user onboarding and session initiation. Its responsibilities include validating registration data, enforcing uniqueness constraints for new accounts, and verifying credentials during login attempts. It coordinates the cryptographic processing of sensitive data and the issuance of session tokens, acting as the logical bridge between the transient authentication request and the persistent user identity.

    \item \textbf{Hash password}: This sub-component is a specialized cryptographic utility dedicated to data integrity and confidentiality. Its sole function is to apply strong, one-way hashing algorithms (typically salted) to user passwords. It ensures that credentials are never stored or processed in plain text, providing the verification mechanism (comparing a candidate password against a stored hash) required during the login process without exposing the underlying secrets.

    \item \textbf{Token manager}: This sub-component manages the lifecycle of security tokens (JSON Web Tokens). It is responsible for two critical security operations: the generation of cryptographically signed tokens upon successful authentication, embedding user claims and expiration policies; and the validation of incoming tokens for protected resources, verifying their signature and validity period to enforce stateless session management.
\end{itemize}

\subsubsection{CMP: Recording service}
\label{sec:cmp_recording_service}


The \texttt{Recording service} component constitutes the core engine for real-time activity tracking on the client side. Designed as a background service to ensure continuity even when the application is minimized, it acts as a centralized controller that manages the acquisition, processing, and temporary persistence of telemetry data from the device's hardware.

\begin{itemize}
    \item \textbf{Recording state manager}: This sub-component acts as the central orchestrator of the recording session. It manages the lifecycle of the activity (Start, Stop) based on commands received from the \texttt{UI layer}. Its primary responsibility is to synchronize the activation and deactivation of the data collection modules (\texttt{GPS tracker} and \texttt{Sensor processor}) and to manage the data flow from the \texttt{sensor manager}.

    \item \textbf{GPS tracker}: This sub-component is specialized in handling geospatial data. It consumes the stream of raw coordinates provided by the hardware, filters noise, and constructs the ordered sequence of \texttt{GPS\_points} that represents the Trip's geometry. It also feeds clean position data to the \texttt{Stats tracker}.

    \item \textbf{Stats tracker}: This sub-component is responsible for the real-time calculation of session metrics. By processing the distance and time deltas from the GPS stream, it computes the user's current speed, average speed, total distance, and elapsed time, providing the \texttt{UI layer} with a continuous stream of updates for the Heads-Up Display (HUD).

    \item \textbf{Sensor processor}: This sub-component implements the logic for automatic obstacle detection (R24). It continuously analyzes the high-frequency data stream from the accelerometer and gyroscope. By applying a threshold-based algorithm, it identifies significant shock events (potential potholes) and creates \texttt{sensor\_event} objects, which are immediately persisted to \texttt{Local storage} for later review.
\end{itemize}

\label{sec:deployment_view}

\noindent \textbf{User Smartphone:} Users access the system using their personal mobile device (iOS or Android) through the dedicated BBP Mobile Application. The device also hosts the external Maps App (e.g., Google Maps) which is triggered by the Mobile App via OS Intents to handle turn-by-turn navigation. The Mobile App communicates with the backend infrastructure via internet connection.

\vspace{0.5em}
\noindent \textbf{Firewall:} It provides a way to limit the attack surface of any potential intruder by providing strict access rules, allowing only secure traffic on port 443 (HTTPS) to reach the Web Server.

\vspace{0.5em}
\noindent \textbf{Web Server:} The Web Server provides access to the Application Server's service to all the Mobile Apps that reach the system. In particular, the Web Server does not execute any business logic, but it simply acts as a gateway and performs load balancing on the received requests, distributing them to the various Application Servers in order to handle large User traffic and terminate SSL connections.

\vspace{0.5em}
\noindent \textbf{Application Server:} The Application Server contains the business logic of the entire system. Moreover, it communicates with the client through the HTTPS protocol managed by the Web Server. The various requests coming from the Web Server are routed to the corresponding internal service (Auth, Path, Trip) thanks to the Controller Layer. Furthermore, it communicates to the Database Server through the Model component via JDBC. This node can be replicated to handle large user traffic and ensure high availability.

\vspace{0.5em}
\noindent \textbf{Database Server:} All the data about Users, Paths, Trips, Reports and the complex geospatial data (GPS tracks) are stored into the Database Server and managed by the PostgreSQL engine with PostGIS extension. The various Application Servers can retrieve and store information on this node through the Model component, which manages the connections. This node is strictly isolated from the public internet.

\vspace{0.5em}
\noindent \textbf{Weather Server:} During the "Save Trip" procedure, the Application Server needs to enrich the trip data with meteorological information. For this scope, the Application Server contacts the external Weather Server through a REST API over HTTPS to retrieve the specific weather conditions for the given time and location.

\section{Selected Architectural Styles and Patterns}
\label{sec:architectural_styles}

The architecture of the Best Bike Paths (BBP) system is designed as a composite structure that integrates several established architectural styles and design patterns. These choices were driven by the specific requirements of the system, such as the need for robust geospatial data handling, clear separation of concerns, and secure data transmission.

\subsection{Architectural Styles}

\subsubsection{Client-Server Architecture}
At the highest level of abstraction, the BBP system adopts a classic \textbf{Client-Server} architectural style. This choice is dictated by the distinct nature of the two main components:
\begin{itemize}
    \item \textbf{The Client (Mobile App):} Responsible for the presentation logic, user interaction, and, critically, the real-time acquisition of sensor data (GPS, accelerometer, gyroscope). It acts as a "thick client" capable of performing local processing (e.g., pothole detection) to reduce network latency and server load.
    \item \textbf{The Server (Backend):} Acts as the centralized source of truth. It is responsible for the heavy-lifting of business logic, data aggregation, security enforcement, and persistent storage.
\end{itemize}
The communication between these two entities is stateless and occurs over a secure RESTful API (HTTPS), ensuring standard interoperability and independent scalability of the client and server components.

\subsubsection{Layered Architecture (Backend)}
Within the Backend Server, we have adopted a \textbf{Layered Architecture} pattern to strictly enforce the separation of concerns. This ensures that each component has a specific responsibility and only interacts with the layers immediately adjacent to it, promoting maintainability and testability. The layers are organized as follows:
\begin{enumerate}
    \item \textbf{Controller Layer (Presentation):} Controller Layer (Presentation \& Orchestration): The outermost layer that handles incoming HTTP requests and input validation. Design Decision: For complex workflows involving multiple independent domain services (e.g., saving a Trip and a Path simultaneously), the Controller also assumes the role of an Orchestrator. This choice was made to prevent tight coupling between domain services (e.g., preventing Trip Service from depending on Path Service), ensuring that each business service remains self-contained and reusable.
    
    \item \textbf{Auth Layer (Middleware):} An intercepting layer responsible for authentication and authorization (JWT validation) before any business logic is executed.
    \item \textbf{Service Layer (Business Logic):} The core of the application (e.g., \texttt{Path Service}, \texttt{Trip Service}). It implements the complex business rules, orchestrates workflows, and performs calculations like path scoring.
    \item \textbf{Data Access Layer (Persistence):} Encapsulated by the \texttt{Model} component, this layer abstracts the underlying database technology, providing a clean API for data storage and retrieval.
\end{enumerate}

\subsection{Design Patterns}

\subsubsection{Repository Pattern}
The \textbf{Repository Pattern} is implemented within the \texttt{Model} component. Its purpose is to decouple the business logic in the Service Layer from the specific details of the database implementation (PostgreSQL/PostGIS). The Services do not write SQL queries directly; instead, they call high-level methods provided by the Model (e.g., \texttt{saveTrip}, \texttt{findPathsByLocation}). This abstraction makes the code cleaner and allows for easier changes to the database schema or technology in the future without affecting the business rules.

\subsubsection{Data Transfer Object (DTO)}
To facilitate efficient data exchange between the Client and the Server, we employ the \textbf{Data Transfer Object (DTO)} pattern. Instead of exposing the internal database entities (which may contain sensitive or redundant information) directly to the API, we define specific classes (DTOs) that encapsulate exactly the data needed for a particular operation. For example, when viewing path details (UC5), a \texttt{PathDetailsDTO} aggregates geometry, weather, status, and statistics into a single packet, reducing the number of network calls ("chattiness") and decoupling the internal domain model from the external interface.

\subsubsection{Facade Pattern}
The \textbf{Facade Pattern} is utilized in multiple areas to simplify interactions with complex subsystems:
\begin{itemize}
    \item \textbf{Controller as Facade:} The Controller layer acts as a facade for the Client, hiding the complexity of the internal service interactions. The client makes a single call (e.g., "Save Trip"), and the Controller handles the internal coordination.
    \item \textbf{Weather API Client:} This component acts as a facade/adapter for the external third-party Weather Service. It abstracts the specific HTTP calls, authentication, and JSON parsing required by the external provider, offering a simple internal interface (e.g., \texttt{getForecast}) to the BBP services.
\end{itemize}

\subsubsection{Transaction Script / Orchestrator}
For complex write operations (UC9, UC12), we explicitly adopted an Orchestrator pattern implemented within the Controller layer. While traditional layered architectures often delegate this to a service, we placed this logic in the Controller to maintain zero coupling between the Path and Trip business domains. The Controller ensures the transactional sequence (Create Path -> Save Reports -> Save Trip), acting effectively as an Application Service or API Gateway for these specific composite use cases.

\subsubsection{Lazy Loading (On-Read Aggregation)}
While not a structural GoF pattern, the decision to calculate the "Path Status" and "Score" dynamically at the time of the request (UC4, UC5) implements a \textbf{Lazy Loading} strategy. This ensures that users always see the most up-to-date information based on the latest "freshness" of reports, avoiding the data consistency issues that would arise from storing a static, pre-calculated score in the database.

\section{Other Design Decisions}
\label{sec:other_design_decisions}

In addition to the primary architectural patterns, several specific design decisions were made to address the system's non-functional requirements, particularly regarding performance, reliability, and operational maintenance.

\subsection{Availability}
To ensure the high availability required by the RASD (PR-2), the system is designed to eliminate single points of failure:
\begin{itemize}
    \item \textbf{Redundancy in Application Tier:} The Application Server is stateless and deployed across multiple instances behind a Load Balancer. If a specific server node fails or becomes unresponsive, the Load Balancer automatically redirects traffic to the remaining healthy nodes, ensuring continuous service for the end-users.
    \item \textbf{Database Clustering:} The persistence layer utilizes a Primary-Replica configuration. While the Primary node handles writes, one or more Standby Replicas replicate data in near real-time. In the event of a critical failure of the Primary node, a failover mechanism promotes a Replica to Primary, minimizing downtime.
    \item \textbf{Graceful Degradation:} The system is designed to handle the unavailability of external services (e.g., Weather API) gracefully. If the Weather API is unreachable during a "Save Trip" operation (UC9), the transaction does not fail; instead, the trip is saved without weather data, and a warning is logged, preserving the core functionality.
\end{itemize}

\subsection{Scalability}
The BBP system is designed to handle varying loads, from daily commutes to peak weekend usage:
\begin{itemize}
    \item \textbf{Horizontal Scaling (Application):} Because the backend services are stateless (authentication is handled via self-contained JWTs), the system can scale horizontally. We can dynamically add or remove Application Server instances based on CPU or RAM usage thresholds without changing the code or configuration.
    \item \textbf{Read/Write Splitting (Database):} The "Search Paths" (UC4) and "View Details" (UC5) operations are read-intensive and constitute the majority of the traffic. The design offloads these read operations to the Database Read Replicas, leaving the Primary Database free to handle write-intensive transactions like "Save Trip" (UC9). This ensures that heavy search traffic does not degrade the performance of data recording.
\end{itemize}

\subsection{Notification Handling and Asynchronous Processing}
While BBP relies primarily on immediate user feedback, internal "system notifications" are handled asynchronously to improve perceived performance:
\begin{itemize}
    \item \textbf{Decoupling Aggregation:} To ensure users consistently access the most up-to-date information regarding path conditions and safety, the system adopts an On-Read Aggregation strategy. In contrast to pre-calculation methods that may yield stale data, the system computes the ``Path Status'' and ``Score'' dynamically at request time. This logic is encapsulated within the stateless \texttt{Path Merger} component, prioritizing data freshness over read latency. To mitigate the performance impact of on-the-fly calculations, the architecture employs optimized PostgreSQL aggregation functions and in-memory dataset processing to minimize database round-trips, potentially supplemented by short-lived caching policies for high-traffic paths.
\end{itemize}

\subsection{Ease of Deployment}
To facilitate smooth updates and consistent environments:
\begin{itemize}
    \item \textbf{Containerization:} All backend components (Application Server, Web Server) are packaged as Docker containers. This ensures that the software runs identically on a developer's machine, the testing environment, and the production cloud infrastructure, eliminating "it works on my machine" issues.
    \item \textbf{Orchestration:} The deployment view suggests the use of a container orchestration platform (such as Kubernetes or a managed Cloud equivalent). This abstracts the hardware management, allowing for automated rolling updates (updating the software without downtime) and self-healing (automatically restarting crashed containers).
\end{itemize}

\subsection{Data Storage}
The choice of \textbf{PostgreSQL} with the \textbf{PostGIS} extension is a strategic design decision:
\begin{itemize}
    \item \textbf{Hybrid Data Handling:} BBP requires strict relational integrity for user accounts and trips (best served by SQL) alongside complex geospatial queries for path finding (e.g., "Find all paths within this bounding box"). PostGIS allows us to handle both data types within a single, transactional database engine.
    \item \textbf{Atomicity:} By using a single database technology, we can wrap complex operations—like saving a Trip, creating a Path, and logging Reports—into a single ACID transaction (UC9), guaranteeing data consistency.
\end{itemize}
