\section{Overview}
\label{sec:Overview}
Here we represents an overview of how the entire BBP architecture is composed of:

\begin{figure}[H]
    \begin{center}
        \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/overview/overview.png}
        \caption{BBP Overview.}
        \label{fig:BBP_overview}%
    \end{center}
\end{figure}
\noindent Client Side:
\begin{itemize}
    \item \textbf{Mobile Client (iOS/Android):} Serves as the primary User Interface (UI) and data collection tool. It provides the native screens for all user interactions, runs a persistent foreground service to continuously capture data from device sensors (GPS, accelerometer, gyroscope), and manages the post-ride summary screen for reviewing events and setting visibility preferences.
\end{itemize}

\noindent Server Side:
\begin{itemize}
    \item \textbf{Backend Server (API \& Core Logic):} Handles all business logic, data integrity, and security via a secure REST API. It processes all incoming data from the client (e.g., saving new trips and paths atomically), manages user authentication, and performs complex server-side operations like aggregating trip statistics to update path averages. It is the single source of truth for all data.
    
    \item \textbf{BBP Database (PostgreSQL + PostGIS):} Stores all data related to users, paths, trips, and reports. It utilizes PostgreSQL for relational data and the \textbf{PostGIS} extension to efficiently store and query all geospatial data (e.g., path geometries, obstacle locations), enabling the core path-searching functionality.
    
    \item \textbf{Device Sensors (GPS, Accelerometer, Gyroscope):} Provides the raw hardware-level data streams to the Mobile Client. The GPS is used to build the trip's geometry, while the \textbf{Accelerometer} and \textbf{Gyroscope} provide motion data used to automatically detect potential obstacles (e.g., potholes).
    
    \item \textbf{External Weather Service:} Utilized by the Backend Server to fetch meteorological data. When a trip is saved, the server queries this API to retrieve weather conditions (e.g., temperature, wind speed) for the trip's time and location, adding valuable context to the user's log.
    
    \item \textbf{External Navigation Service:} Invoked by the Mobile Client to provide turn-by-turn directions. When a user "Follows Path," the client sends the route's destination or geometry to the device's default mapping application, allowing BBP to focus on its core recording and evaluation features.
\end{itemize}

This diagram defines the high-level system boundaries and the primary components of the Best Bike Paths (BBP) system. It illustrates a classic client-server architecture, clearly separating the client-side data collection components from the server-side business logic and persistence components.



\noindent \textbf{Mobile App} \\
Serves as the external access point for users and the primary data collection tool. It allows communication with the \texttt{BBP backend server} through the \texttt{BBP API}, which is the sole interface for all server-side business logic (like searching paths and saving trips). The \texttt{Mobile App} also requires raw data from the \texttt{Device sensor} component via the \texttt{Device info} interface for live recording and triggers the \texttt{External navigation service} using the \texttt{Navigation service} interface.

\vspace{0.5em} % Aggiunge un po' di spazio tra i paragrafi

\noindent \textbf{BBP backend server} \\
Serves as the central authority for all business logic, security, and persistence. It \textit{provides} the \texttt{BBP API} to handle all incoming requests from the \texttt{Mobile App}. To fulfill these requests, it requires access to the \texttt{BBP Database} through the \texttt{DBMS API} for all data storage, and also queries the \texttt{External weather service} via the \texttt{Weather info API} to enrich trip data.

\vspace{0.5em}

\noindent \textbf{Device sensor} \\
Acts as the hardware-level data provider, representing the phone's GPS, accelerometer, and gyroscope. It \textit{provides} the \texttt{Device info} interface, which is consumed exclusively by the \texttt{Mobile App} to stream the raw location and motion data necessary for trip recording.

\vspace{0.5em}

\noindent \textbf{External navigation service} \\
A third-party mapping application (e.g., Google Maps) that \textit{provides} the \texttt{Navigation service} interface (e.g., an OS-level Intent or URL scheme). It is triggered by the \texttt{Mobile App} to launch and provide the user with turn-by-turn directions.

\vspace{0.5em}

\noindent \textbf{BBP Database} \\
The system's core persistence component, utilizing PostgreSQL and PostGIS. It \textit{provides} the \texttt{DBMS API}, which is consumed exclusively by the \texttt{BBP backend server} to store and retrieve all application data, including user accounts, paths, trips, and geospatial tracks.

\vspace{0.5em}

\noindent \textbf{External weather service} \\
A third-party data provider that \textit{provides} the \texttt{Weather info API}. This interface is consumed by the \texttt{BBP backend server} (and \textit{not} the client) to fetch meteorological data, such as temperature and wind conditions, when a new trip is saved.

\subsection*{Mobile App (Client) Component Descriptions}
\begin{itemize}
    \item \textbf{UI layer:} This is the central hub for all user interaction within the \texttt{Mobile App}. It receives user input and orchestrates the other client-side components by sending commands through various interfaces, such as the \texttt{recording interface} (to the \texttt{recording service}) and the \texttt{Navigation interface} (to the \texttt{navigation manager}). It also receives data to display, consuming the \texttt{HUD interface} from the \texttt{recording service} for live stats and the \texttt{connection interface} from the \texttt{Network layer}.
    
    \item \textbf{sensor manager:} This component's function is to abstract the complex hardware of the \texttt{Device sensor} (GPS, gyroscope, accelerometer). It consumes the raw data from the \texttt{Device sensor interface} and provides a clean, processed data stream to the \texttt{recording service} via the \texttt{Sensor interface}.
    
    \item \textbf{recording service:} This is the core component for all trip recording (UC7). It runs as a background service, activated by the \texttt{UI layer} via the \texttt{recording interface}. It consumes the data stream from the \texttt{sensor manager} to build the trip track and detect obstacles. It provides the \texttt{HUD interface} back to the \texttt{UI layer} with real-time statistics (R22) and sends the final trip data to both the \texttt{Network layer} and \texttt{Local storage} via the \texttt{Saving interface}.
    
    \item \textbf{navigation manager:} This component handles the external navigation functionality (UC6). It is triggered by the \texttt{UI layer} (via the \texttt{Navigation interface}) and communicates with the \texttt{Network layer} (via the \texttt{connection interface}) to get route information, before finally launching the external app through the \texttt{Navigation service} interface.
    
    \item \textbf{Network layer:} This component is responsible for all communication with the \texttt{BBP backend server}. It consumes the \texttt{BBP API} (provided by the \texttt{Controller layer}) using the HTTPS/REST protocol. It also fetches data to be sent by consuming the \texttt{Saving interface} from both the \texttt{recording service} and \texttt{Local storage} (to sync cached data).
    
    \item \textbf{Local storage:} This component handles on-device persistence (e.g., SQLite for caching trips, SharedPreferences for auth tokens). It consumes the \texttt{Saving interface} from the \texttt{recording service} to save trip data locally. It provides data back to the \texttt{Network layer} (for synchronization) and the \texttt{UI layer} (for retrieving tokens/settings).
\end{itemize}

\subsection*{BBP backend server Component Descriptions}
\begin{itemize}
    \item \textbf{Controller layer:} This component is the single entry point (Facade) for the entire backend. It provides the \texttt{BBP API} that the \texttt{Network layer} consumes. Its primary job is to parse incoming JSON requests and route them to the correct internal service, either to the \texttt{authentication interface} (for public routes like login) or to the \texttt{Security interface} (for all protected routes).
    
    \item \textbf{Security module:} This component acts as the central authorization gate (middleware) for the system. It consumes requests from the \texttt{Controller layer} via the \texttt{Security interface}. It validates the user's JWT token by communicating with the \texttt{Auth service}. If the request is valid, it forwards the request to the appropriate service through the \texttt{Path interface}, \texttt{Trip interface}, or \texttt{Profile interface}.
    
    \item \textbf{Auth service:} This component handles all business logic related to user identity (UC1, UC2). It provides the \texttt{authentication interface}, which is used by the \texttt{Controller layer} (for login/register) and the \texttt{Security module} (for token validation). It communicates with the \texttt{Model} component (via the \texttt{Model interface}) to create or retrieve user data from the \texttt{BBP Database}.
    
    \item \textbf{Profile manager:} This component manages user-specific data that is not related to authentication (e.g., name, email, user settings). It receives authorized requests from the \texttt{Security module} via the \texttt{Profile interface} and communicates with the \texttt{Model} component to read or update user profile information.
    
    \item \textbf{Path service:} This component handles all business logic related to \texttt{Paths} (UC4, UC5). It receives authorized requests from the \texttt{Security module} via the \texttt{Path interface}. It communicates with the \texttt{Model} to perform complex geospatial searches (R9) and retrieves data from the \texttt{Weather API client} (via the \texttt{Weather interface}) to get real-time *forecasts* for a selected path (R14).
    
    \item \textbf{Trip service:} This component handles all business logic for individual \texttt{Trips} (UC9, UC13). It receives authorized requests from the \texttt{Security module} via the \texttt{Trip interface}. It communicates with the \texttt{Model} to save new trips or retrieve a user's trip history. It also communicates with the \texttt{Weather API client} (via the \texttt{Weather interface}) to fetch a *historical snapshot* of the weather when a trip is saved (R32).
    
    \item \textbf{Model:} This component is the Data Access Layer (DAL) for the entire application, implementing the Repository Pattern. It provides the central \texttt{Model interface} that is consumed by all services (\texttt{Auth}, \texttt{Profile}, \texttt{Path}, \texttt{Trip}). It is the only component that communicates with the \texttt{BBP Database}, translating internal data requests into \texttt{SQL/ORM} commands via the \texttt{DBMS API}.
    
    \item \textbf{Weather API client:} This is a wrapper component whose sole function is to manage communication with the \texttt{External weather service}. It provides the \texttt{Weather interface} (consumed by both \texttt{Path service} and \texttt{Trip service}) and translates those calls into external HTTPS/REST requests, consuming the \texttt{Weather API}.
\end{itemize}




\subsubsection{CMP: Path service}
\label{sec:cmp_path_service}

\begin{figure}[H]
    \begin{center}
        \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/componentDiagrams/Component_diagram-path_detailed_view.drawio.png}
        \caption{Path service}
        \label{fig:Path service}%
    \end{center}
\end{figure}

\noindent This component manages all business logic related to \texttt{Paths}, including their manual creation (UC11), searching (UC4), and detailed viewing (UC5). It implements a full "On-Read" aggregation strategy. It exposes a single \texttt{Path interface} port to the \texttt{Security module}, which internally routes requests to three specialized interfaces.

\begin{itemize}
    \item \textbf{path adding:} This module handles the logic for manually creating a new \texttt{Path}. It is activated by the \texttt{Path adding interface} and its sole responsibility is to communicate with the \texttt{Model} component (via the \texttt{Model interface}) to persist the new \texttt{Path} entity in the database.
    
    \item \textbf{Path searcher:} This module handles the primary search functionality (UC4). It is activated by the \texttt{Search path interface}. It implements the "On-Read" (lazy) aggregation logic by communicating with two components:
    \begin{itemize}
        \item The \texttt{Model} (via the \texttt{Model interface}): to retrieve the \texttt{Paths} themselves, all associated public \texttt{Trips} (for live statistics calculation), and all \texttt{Reports}.
        \item The \texttt{Path merger} (via the \texttt{Path merger interface}): to calculate the "fresh" status (R9) from the retrieved reports.
    \end{itemize}
    
    \item \textbf{Detailed path view:} This module handles the logic for fetching a single, detailed \texttt{Path} (UC5). It is activated by the \texttt{Detailed path interface}. This is the most complex read operation, as it communicates with three components to build the final view:
    \begin{itemize}
        \item The \texttt{Model} (via the \texttt{Model interface}): for all core path, trip, and report data.
        \item The \texttt{Path merger} (via the \texttt{Path merger interface}): for the "fresh" status.
        \item The \texttt{Weather API client} (via the \texttt{Weather interface}): to fetch the current weather *forecast* for the path's location (R14).
    \end{itemize}
    
    \item \textbf{Path merger:} This is an internal "worker" module that implements the \textit{On-Read} logic for calculating the path status (R9). It \textit{provides} the \texttt{Path merger interface} (consumed by \texttt{Path searcher} and \texttt{Detailed path view}). To perform its calculation, it communicates with the \texttt{Model} component (via the \texttt{Model interface}) to retrieve the necessary \texttt{Status\_reports}.
\end{itemize}

\noindent This component is responsible for all business logic related to individual \texttt{Trips}, including their creation (UC9) and retrieval (UC13). It exposes a single facade port to the \texttt{Security module}, which internally routes requests to two specialized interfaces: \texttt{Trip adding interface} and \texttt{Trip search interface}.

\begin{itemize}
    \item \textbf{trip adding:} This module handles the complex orchestration of saving a new \texttt{Trip} (UC9). It \textit{provide} the \texttt{Trip adding interface} to receive the trip data. To execute the save operation, it \textit{consumes} (requires) two critical interfaces:
    \begin{itemize}
        \item The \texttt{Weather interface} (from the \texttt{Weather API client}) to fetch the snapshot of the weather conditions for the trip (R32).
        \item The \texttt{Model interface} (from the \texttt{Model}) to atomically save the new \texttt{Trip}, its associated \texttt{Path}, and any confirmed \texttt{Reports} to the database (R33).
    \end{itemize}
    
    \item \textbf{trip searcher:} This module handles the retrieval of a user's personal trip history (UC13). It \textit{provides} the \texttt{Trip search interface}. It executes a simple read operation by \textit{consuming} (requiring) the \texttt{Model interface} to fetch the list of \texttt{Trips} associated with the user's ID.
\end{itemize}

\noindent This component manages all business logic for user identity (UC1, UC2). It serves a dual role: it provides public-facing services for registration and login (triggered by the \texttt{Controller layer}), and it also provides a private, internal service for token validation (consumed by the \texttt{Security module}).

\begin{itemize}
    \item \textbf{user service:} This is the central orchestrator for all authentication logic, directly containing the business rules for registration and login. It \textit{consumes} (requires) the \texttt{authentication interface} provided by the external \texttt{Controller layer}. To execute its tasks, it \textit{consumes} (requires) three distinct interfaces:
    \begin{itemize}
        \item The \texttt{Hashing interface} (provided by \texttt{Hash password}).
        \item The \texttt{token creation interface} (provided by \texttt{token manager}).
        \item The \texttt{Model interface} (provided by the external \texttt{Model}).
    \end{itemize}
    
    \item \textbf{Hash password:} A specialized utility module that \textit{provides} the \texttt{Hashing interface}. Its sole function is to securely hash new passwords to verify existing hashes during login or to compare during registration, consumed by the \texttt{user service}.
    
    \item \textbf{token manager:} This module is responsible for all \textbf{JWT} (JSON Web Token) operations. It \textit{provides} two distinct interfaces:
    \begin{itemize}
        \item The \texttt{token creation interface}, which is consumed by the \texttt{user service} to generate a new session token upon successful login.
        \item The \texttt{validation interface}, which is consumed by the external \texttt{Security module} to validate tokens for all protected API requests.
    \end{itemize}
\end{itemize}

\subsubsection{CMP: Recording service}
\label{sec:cmp_recording_service}

\noindent This component package contains the core client-side logic for the trip recording functionality (UC7). It is designed as a background service orchestrated by an internal \texttt{Recording state manager} that commands several specialized sub-modules. It receives commands from the \texttt{UI layer} and raw data from the \texttt{sensor manager}.

\begin{itemize}
    \item \textbf{Recording state manager:} This is the central "brain" or orchestrator of the service. It \textit{consumes} (requires) the \texttt{Recording interface} from the \texttt{UI layer} (to receive start/stop commands) and the \texttt{Sensor interface} from the \texttt{sensor manager} (to receive the raw hardware data stream). It, in turn, \textit{provides} (controls) command interfaces to its "worker" modules: the \texttt{GPS point interface} (for the \texttt{GPS tracker}) and the \texttt{Processing sensor interface} (for the \texttt{Sensor processor}).
    
    \item \textbf{GPS tracker:} This module's sole responsibility is to manage the GPS data stream. It \textit{consumes} (requires) the \texttt{GPS point interface} from the \texttt{Recording state manager}. It \textit{provides} a data interface (the stream of \texttt{GPS\_points}) that is consumed by the \texttt{Stats tracker} for calculations.
    
    \item \textbf{Sensor processor:} This module is responsible for analyzing the high-frequency motion sensor data (R24) to detect potential obstacles. It \textit{consumes} (requires) the \texttt{Processing sensor interface} from the \texttt{Recording state manager}. When a significant event (e.g., a pothole) is detected, it \textit{consumes} (requires) the \texttt{Saving interface} from the \texttt{Local storage} component to persist this \texttt{sensor\_event} locally.
    
    \item \textbf{Stats tracker:} This module is responsible for calculating real-time statistics (R22) for the user. It \textit{consumes} (requires) the data interface provided by the \texttt{GPS tracker} to calculate distance and speed. It \textit{provides} the \texttt{HUD interface}, which is consumed by the external \texttt{UI layer} to display live statistics to the user.
\end{itemize}


\section{Deployment View}
\label{sec:deployment_view}

In this section it will be shown the Deployment diagram of the BBP system, followed by a description of the components and their interactions:

\begin{figure}[H]
    \centering
    % Inserisci qui il percorso della tua immagine
    \includegraphics[width=1\linewidth]{DD/LaTeXCode/images/deploymentDiagrams/deploymentDiagram.png}
    \caption{Deployment Diagram.}
    \label{fig:deployment_diagram}
\end{figure}

\noindent \textbf{User Smartphone:} Users access the system using their personal mobile device (iOS or Android) through the dedicated BBP Mobile Application. The device also hosts the external Maps App (e.g., Google Maps) which is triggered by the Mobile App via OS Intents to handle turn-by-turn navigation. The Mobile App communicates with the backend infrastructure via internet connection.

\vspace{0.5em}
\noindent \textbf{Firewall:} It provides a way to limit the attack surface of any potential intruder by providing strict access rules, allowing only secure traffic on port 443 (HTTPS) to reach the Web Server.

\vspace{0.5em}
\noindent \textbf{Web Server:} The Web Server provides access to the Application Server's service to all the Mobile Apps that reach the system. In particular, the Web Server does not execute any business logic, but it simply acts as a gateway and performs load balancing on the received requests, distributing them to the various Application Servers in order to handle large User traffic and terminate SSL connections.

\vspace{0.5em}
\noindent \textbf{Application Server:} The Application Server contains the business logic of the entire system. Moreover, it communicates to the client through HTTPS protocol managed by the Web Server. The various requests coming from the Web Server are routed to the corresponding internal service (Auth, Path, Trip) thanks to the Controller Layer. Furthermore, it communicates to the Database Server through the Model component via JDBC. This node is replicated in order to handle large user traffic and ensure high availability.

\vspace{0.5em}
\noindent \textbf{Database Server:} All the data about Users, Paths, Trips, Reports and the complex geospatial data (GPS tracks) are stored into the Database Server and managed by the PostgreSQL engine with PostGIS extension. The various Application Servers can retrieve and store information on this node through the Model component, which manages the connections. This node is strictly isolated from the public internet.

\vspace{0.5em}
\noindent \textbf{Weather Server:} During the "Save Trip" procedure, the Application Server needs to enrich the trip data with meteorological information. For this scope, the Application Server contacts the external Weather Server through a REST API over HTTPS to retrieve the specific weather conditions for the given time and location.

\noindent This diagram illustrates the search functionality, implementing the \textbf{"On-Read" aggregation strategy} with a performance optimization.
\begin{itemize}

    \item \textbf{In-Memory Processing:} The \textbf{Path searcher} iterates through the retrieved raw data in memory. It delegates the logic to the \textbf{Path merger}, which acts as a stateless calculation engine to determine the path's status and score without making further database calls.
\end{itemize}

\noindent This sequence diagram illustrates the retrieval of comprehensive information for a specific path selected by the user. \section{Selected Architectural Styles and Patterns}
\label{sec:architectural_styles}

The architecture of the Best Bike Paths (BBP) system is designed as a composite structure that integrates several established architectural styles and design patterns. These choices were driven by the specific requirements of the system, such as the need for robust geospatial data handling, clear separation of concerns, and secure data transmission.

\subsection{Architectural Styles}

\subsubsection{Client-Server Architecture}
At the highest level of abstraction, the BBP system adopts a classic \textbf{Client-Server} architectural style. This choice is dictated by the distinct nature of the two main components:
\begin{itemize}
    \item \textbf{The Client (Mobile App):} Responsible for the presentation logic, user interaction, and, critically, the real-time acquisition of sensor data (GPS, accelerometer, gyroscope). It acts as a "thick client" capable of performing local processing (e.g., pothole detection) to reduce network latency and server load.
    \item \textbf{The Server (Backend):} Acts as the centralized source of truth. It is responsible for the heavy-lifting of business logic, data aggregation, security enforcement, and persistent storage.
\end{itemize}
The communication between these two entities is stateless and occurs over a secure RESTful API (HTTPS), ensuring standard interoperability and independent scalability of the client and server components.

\subsubsection{Layered Architecture (Backend)}
Within the Backend Server, we have adopted a \textbf{Layered Architecture} pattern to strictly enforce the separation of concerns. This ensures that each component has a specific responsibility and only interacts with the layers immediately adjacent to it, promoting maintainability and testability. The layers are organized as follows:
\begin{enumerate}
    \item \textbf{Controller Layer (Presentation):} The outermost layer that handles incoming HTTP requests, performs input validation, and routes them to the appropriate business logic. It acts as the interface to the outside world.
    \item \textbf{Security Layer (Middleware):} An intercepting layer responsible for authentication and authorization (JWT validation) before any business logic is executed.
    \item \textbf{Service Layer (Business Logic):} The core of the application (e.g., \texttt{Path Service}, \texttt{Trip Service}). It implements the complex business rules, orchestrates workflows, and performs calculations like path scoring.
    \item \textbf{Data Access Layer (Persistence):} Encapsulated by the \texttt{Model} component, this layer abstracts the underlying database technology, providing a clean API for data storage and retrieval.
\end{enumerate}

\subsection{Design Patterns}

\subsubsection{Repository Pattern}
The \textbf{Repository Pattern} is implemented within the \texttt{Model} component. Its purpose is to decouple the business logic in the Service Layer from the specific details of the database implementation (PostgreSQL/PostGIS). The Services do not write SQL queries directly; instead, they call high-level methods provided by the Model (e.g., \texttt{saveTrip}, \texttt{findPathsByLocation}). This abstraction makes the code cleaner and allows for easier changes to the database schema or technology in the future without affecting the business rules.

\subsubsection{Data Transfer Object (DTO)}
To facilitate efficient data exchange between the Client and the Server, we employ the \textbf{Data Transfer Object (DTO)} pattern. Instead of exposing the internal database entities (which may contain sensitive or redundant information) directly to the API, we define specific classes (DTOs) that encapsulate exactly the data needed for a particular operation. For example, when viewing path details (UC5), a \texttt{PathDetailsDTO} aggregates geometry, weather, status, and statistics into a single packet, reducing the number of network calls ("chattiness") and decoupling the internal domain model from the external interface.

\subsubsection{Facade Pattern}
The \textbf{Facade Pattern} is utilized in multiple areas to simplify interactions with complex subsystems:
\begin{itemize}
    \item \textbf{Controller as Facade:} The Controller layer acts as a facade for the Client, hiding the complexity of the internal service interactions. The client makes a single call (e.g., "Save Trip"), and the Controller handles the internal coordination.
    \item \textbf{Weather API Client:} This component acts as a facade/adapter for the external third-party Weather Service. It abstracts the specific HTTP calls, authentication, and JSON parsing required by the external provider, offering a simple internal interface (e.g., \texttt{getForecast}) to the BBP services.
\end{itemize}

\subsubsection{Transaction Script / Orchestrator}
For complex write operations, specifically the "Save Trip and Path" (UC9) and "Save Path" (UC12) scenarios, we adopted a \textbf{Transaction Script} or \textbf{Orchestrator} approach implemented within the Controller layer. Instead of distributing the logic of creating paths, saving reports, and linking trips across disparate components, the Controller acts as a central orchestrator. It executes these steps in a precise, sequential order (Create Path $\rightarrow$ Save Reports $\rightarrow$ Save Trip), ensuring transactional integrity. If any step fails, the entire logical operation can be rolled back or handled as an error, preventing inconsistent data states (e.g., a Trip linked to a non-existent Path).

\subsubsection{Lazy Loading (On-Read Aggregation)}
While not a structural GoF pattern, the decision to calculate the "Path Status" and "Score" dynamically at the time of the request (UC4, UC5) implements a \textbf{Lazy Loading} strategy. This ensures that users always see the most up-to-date information based on the latest "freshness" of reports, avoiding the data consistency issues that would arise from storing a static, pre-calculated score in the database.

\section{Other Design Decisions}
\label{sec:other_design_decisions}

In addition to the primary architectural patterns, several specific design decisions were made to address the system's non-functional requirements, particularly regarding performance, reliability, and operational maintenance.

\subsection{Availability}
To ensure the high availability required by the RASD (PR-2), the system is designed to eliminate single points of failure:
\begin{itemize}
    \item \textbf{Redundancy in Application Tier:} The Application Server is stateless and deployed across multiple instances behind a Load Balancer. If a specific server node fails or becomes unresponsive, the Load Balancer automatically redirects traffic to the remaining healthy nodes, ensuring continuous service for the end-users.
    \item \textbf{Database Clustering:} The persistence layer utilizes a Primary-Replica configuration. While the Primary node handles writes, one or more Standby Replicas replicate data in near real-time. In the event of a critical failure of the Primary node, a failover mechanism promotes a Replica to Primary, minimizing downtime.
    \item \textbf{Graceful Degradation:} The system is designed to handle the unavailability of external services (e.g., Weather API) gracefully. If the Weather API is unreachable during a "Save Trip" operation (UC9), the transaction does not fail; instead, the trip is saved without weather data, and a warning is logged, preserving the core functionality.
\end{itemize}

\subsection{Scalability}
The BBP system is designed to handle varying loads, from daily commutes to peak weekend usage:
\begin{itemize}
    \item \textbf{Horizontal Scaling (Application):} Because the backend services are stateless (authentication is handled via self-contained JWTs), the system can scale horizontally. We can dynamically add or remove Application Server instances based on CPU or RAM usage thresholds without changing the code or configuration.
    \item \textbf{Read/Write Splitting (Database):} The "Search Paths" (UC4) and "View Details" (UC5) operations are read-intensive and constitute the majority of the traffic. The design offloads these read operations to the Database Read Replicas, leaving the Primary Database free to handle write-intensive transactions like "Save Trip" (UC9). This ensures that heavy search traffic does not degrade the performance of data recording.
\end{itemize}

\subsection{Notification Handling and Asynchronous Processing}
While BBP relies primarily on immediate user feedback, internal "system notifications" are handled asynchronously to improve perceived performance:
\begin{itemize}
    \item \textbf{Decoupling Aggregation:} As seen in the design of the \texttt{Trip Service}, the recalculation of path statistics (R9) is triggered via an \texttt{Aggregation Publisher}. This allows the critical "Save Trip" transaction to complete and return a success message to the user immediately, while the heavy computational task of updating the path's average statistics happens asynchronously in the background (On-Write strategy). This prevents user interface freezing during complex server-side calculations.
\end{itemize}

\subsection{Ease of Deployment}
To facilitate smooth updates and consistent environments:
\begin{itemize}
    \item \textbf{Containerization:} All backend components (Application Server, Web Server) are packaged as Docker containers. This ensures that the software runs identically on a developer's machine, the testing environment, and the production cloud infrastructure, eliminating "it works on my machine" issues.
    \item \textbf{Orchestration:} The deployment view suggests the use of a container orchestration platform (like Kubernetes or a managed Cloud equivalent). This abstracts the hardware management, allowing for automated rolling updates (updating the software without downtime) and self-healing (automatically restarting crashed containers).
\end{itemize}

\subsection{Data Storage}
The choice of \textbf{PostgreSQL} with the \textbf{PostGIS} extension is a strategic design decision:
\begin{itemize}
    \item \textbf{Hybrid Data Handling:} BBP requires strict relational integrity for user accounts and trips (best served by SQL) alongside complex geospatial queries for path finding (e.g., "Find all paths within this bounding box"). PostGIS allows us to handle both data types within a single, transactional database engine.
    \item \textbf{Atomicity:} By using a single database technology, we can wrap complex operations—like saving a Trip, creating a Path, and logging Reports—into a single ACID transaction (UC9), guaranteeing data consistency.
\end{itemize}
